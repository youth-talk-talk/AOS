# Overview  
Android 앱 "AOS"의 REST API 테스트 코드를 체계적으로 개발하여 모든 API 엔드포인트의 정확성과 안정성을 보장한다. 각 API별로 순차적으로 테스트 코드를 작성하여 MockWebServer를 활용한 통합 테스트 환경을 구축한다.

# Core Features  
- MockWebServer 기반 테스트 환경 구축
- 6개 주요 API 서비스 테스트 코드 개발 (Login, Policy, Community, User, Comment, Announce)
- 테스트 데이터 모델 및 유틸리티 개발
- API 응답 검증 및 예외 처리 테스트
- 테스트 커버리지 및 품질 보장

# User Experience  
개발자가 API 테스트를 통해 다음을 확인할 수 있어야 함:
- API 요청/응답 정확성
- 네트워크 오류 처리
- 데이터 직렬화/역직렬화
- 인증 및 권한 검증

# Technical Architecture  
## 기술 스택
- MockWebServer: 로컬 HTTP 서버 시뮬레이션
- JUnit5: 테스트 프레임워크
- Kotlin Coroutines: 비동기 처리
- Retrofit: HTTP 클라이언트
- Gson/Moshi: JSON 직렬화

## 모듈 구조
- core/data/src/test/java/com/youthtalk/data/
  - api/ (API 서비스별 테스트)
  - utils/ (테스트 유틸리티)
  - models/ (테스트 데이터 모델)

## API 서비스 목록
1. LoginService - 로그인/인증 API
2. PolicyService - 정책/약관 API  
3. CommunityService - 커뮤니티 API
4. UserService - 사용자 API
5. CommentService - 댓글 API
6. AnnounceService - 공지사항 API

# Development Roadmap  
## Phase 1: 기반 구조 설정 (24시간)
### 1.1 MockWebServer 설정
- MockWebServer 기본 설정 및 초기화
- 테스트용 HTTP 서버 시작/종료 로직
- 기본 요청/응답 핸들링

### 1.2 테스트 유틸리티 개발
- API 클라이언트 테스트 헬퍼
- 공통 응답 검증 함수
- 테스트 데이터 팩토리

### 1.3 테스트 데이터 모델
- Mock 응답 데이터 클래스
- 테스트용 DTO/Entity 모델
- 오류 응답 모델

## Phase 2: API 서비스별 테스트 개발 (80시간)
### 2.1 LoginService 테스트 (12시간)
- 로그인 API 성공 케이스
- 잘못된 credentials 처리
- 토큰 갱신 로직
- 로그아웃 API

### 2.2 PolicyService 테스트 (10시간)
- 정책 목록 조회
- 특정 정책 상세 조회
- 정책 동의 처리

### 2.3 CommunityService 테스트 (20시간)
- 게시글 목록 조회 (페이징)
- 게시글 상세 조회
- 게시글 작성/수정/삭제
- 게시글 검색 기능

### 2.4 UserService 테스트 (15시간)
- 사용자 프로필 조회
- 프로필 업데이트
- 사용자 설정 관리
- 친구/팔로우 기능

### 2.5 CommentService 테스트 (12시간)
- 댓글 목록 조회
- 댓글 작성/수정/삭제
- 대댓글 처리
- 댓글 좋아요/신고

### 2.6 AnnounceService 테스트 (11시간)
- 공지사항 목록 조회
- 공지사항 상세 조회
- 중요 공지 필터링
- 읽음 상태 관리

# Logical Dependency Chain
1. **기반 설정 우선**: MockWebServer 설정 → 테스트 유틸리티 → 데이터 모델
2. **인증 기반 API 우선**: LoginService (다른 API의 인증 토큰 필요)
3. **핵심 기능 순서**: PolicyService → UserService (사용자 정보 기반)
4. **컨텐츠 API**: CommunityService → CommentService (게시글 기반 댓글)
5. **시스템 API**: AnnounceService (독립적 기능)

# Risks and Mitigations  
## 기술적 위험
- MockWebServer 설정 복잡성 → 단계별 설정 가이드 작성
- API 응답 스키마 변경 → 버전별 테스트 데이터 관리
- 테스트 간 격리 실패 → 각 테스트별 서버 인스턴스 분리

## 개발 위험
- API 의존성 복잡도 → 명확한 순서 정의 및 단위별 검증
- 테스트 데이터 유지보수 → 중앙화된 팩토리 패턴 적용

# Appendix  
## 코딩 표준
- Kotlin 코딩 컨벤션 준수
- 테스트 메서드명: `given_when_then` 패턴

- Given-When-Then 구조로 테스트 작성

- 코드 커버리지 85% 이상
- 모든 HTTP 상태 코드 케이스 커버
